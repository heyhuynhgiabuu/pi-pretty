# pi-pretty 0.6.24

## Summary

Fixes the extension-load crash on pi 0.84.3 when pi-pretty is installed as a managed pi package, and updates the pi dependency line to ^0.84.3.

## What changed

- **ESM package output (`"type": "module"`):** pi-coding-agent 0.84.3 added `dist/modes/interactive/session-share.js`, which imports `@earendil-works/pi-ai/providers/radius-config`. Unbundled npm installs of pi load extensions through jiti with an alias table that maps bare `@earendil-works/pi-ai` to its `dist/compat.js` bundle but only enumerates `/compat`, `/oauth`, and `/providers/all` subpaths explicitly. With CommonJS extension output, the whole SDK import graph was processed through that alias pipeline, and jiti's longest-prefix matching concatenated the uncovered subpath onto the alias value, yielding the nonexistent module `.../pi-ai/dist/compat.js/providers/radius-config`. Any extension whose import graph touched the SDK barrel therefore failed to start (the failure was silent in `pi -ne`, which skips extensions). Shipping true ESM keeps the source unchanged (tsconfig was already `module: nodenext`) while making runtime SDK imports resolve natively through Node's exports maps, which the alias pipeline never touches.
- **pi dependencies:** `@earendil-works/pi-ai`, `@earendil-works/pi-coding-agent`, and `@earendil-works/pi-tui` moved from `^0.82.0` to `^0.84.3`.

## Why

- Managed-package installs are the standard way users add pi-pretty to pi, and on pi 0.84.3 every such install crashed at startup. The regression came from the host release train (session sharing), not from pi-pretty's own code — proven by A/B: the identical test suite passes on pi 0.82.1 and fails on 0.84.3 before this fix.
