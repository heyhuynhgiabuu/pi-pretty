# pi-pretty 0.6.23

## Summary

Fixes silent syntax-highlighting degradation for native pi users and makes every option configurable through `pi-pretty.json` with environment variables as the override layer.

## What changed

- **Theme validation (issue #11):** pi's `~/.pi/agent/settings.json` `theme` field is a TUI appearance setting (`dark`/`light`/custom pi theme names), not a Shiki theme name. Passing it into Shiki made `codeToANSI` throw and the bare catch silently rendered every highlighted block as plain text. `resolveTheme()` now validates both `PRETTY_THEME` and the `settings.json` candidate against Shiki's bundled themes (via `Object.hasOwn`), emits a one-time warning naming the source, and falls back to `github-dark`. The documented fallback chain is preserved.
- **Full config file support (issue #12):** `pi-pretty.json` now accepts `theme`, `icons`, `enableTools`, `disableTools`, `maxHlChars`, `maxPreviewLines`, `cacheLimit` alongside `background`. Precedence is 12-factor: **env var > pi-pretty.json > built-in default** (the theme chain additionally includes `~/.pi/agent/settings.json` before the default). All existing env vars are retained and win when set (empty string = unset). Config is validated (invalid fields silently skipped) and loaded once at extension activation; theme resolution became lazy so config values apply. `PRETTY_CONFIG_DIR` stays env-only.

## Why

- Native pi users (no custom theme plugin) had zero syntax highlighting with no warning — line numbers rendered but colors silently disappeared.
- Configuration was split across two inconsistent systems with no documented rationale: a config file that only handled backgrounds and seven env-only options. The least discoverable mechanism (shell env) controlled the most commonly tuned options (theme, the opt-in `ls` feature).
